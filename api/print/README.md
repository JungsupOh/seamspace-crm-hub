# /print — 일기 제본 PDF 생성

일기 사용자가 쓴 일기를 인쇄용 PDF(154×216mm)로 만든다. 지금은 **관리자 전용**이다.

관리자가 마음일기 계정으로 로그인 → 대상 사용자 아이디 입력 → 일기 현황과 견적 확인
→ 버튼 한 번으로 PDF 생성·다운로드.

- 화면: `src/pages/Print.tsx`, `src/lib/print.ts`
- 서버: `api/print/*.py` (Vercel Python 함수)
- 원본: `mDiary_report/reportsD.py` — 로컬에서 username 을 고쳐 가며 돌리던 스크립트

`/shop` 에는 이미 `diary`(나의 이야기 출력 서비스) 상품이 같은 가격표로 등록되어 있다
(`supabase/add_diary_print_product.sql`). 즉 **주문·결제는 이미 있고 비어 있던 건
"일기를 실제로 PDF 로 만들어내는" 이행 부분**이며, 이 기능이 그 절반을 채운다.

---

## 왜 Python 인가 (Edge Function 이 아니라)

렌더러가 reportlab 기반이다. Supabase Edge Function 은 Deno 라 여기서 돌릴 수 없다.
템플릿이 인쇄 규격에 맞춰 좌표 단위로 맞춰져 있어 TypeScript 로 다시 쓰는 건
인쇄 품질을 걸고 하는 도박이라 하지 않았다.

Vercel 은 Vite 프론트엔드와 Python 함수를 한 프로젝트에서 같이 빌드한다.
`reportlab` 은 순수 파이썬 휠(`py3-none-any`)이라 그대로 동작한다.
함수 하나가 약 58MB(에셋 20MB + reportlab·Pillow) — Vercel 상한 250MB.

**가격 계산도 Python 한 곳에만 둔다.** 화면에 같은 계산을 복사하면 언젠가 어긋나고,
어긋나면 26,000원으로 견적한 책이 160페이지로 인쇄되는 돈 문제가 된다. 그래서 화면은
구간이나 분책 경계를 바꿀 때마다 `/api/print/quote` 를 부른다(일기 재조회 없는 순수 계산).

## 구성

```
api/print/
  login.py       {username, password}          -> {token, name}   관리자만 통과
  stats.py       {token, username}              -> 월별 집계 + 견적
  quote.py       {monthly, from, to, splits?}   -> 견적만 재계산 (인증 불필요, 순수 계산)
  generate.py    {token, username, from, to}    -> PDF 1권 생성 → Storage → signed URL
  _lib/
    render.py    reportsD.py 를 옮긴 렌더러
    pricing.py   가격 구간, 월 경계 분권
    mdiary.py    마음일기 API 클라이언트
    emoji.py     이모지 렌더링
    storage.py   Supabase Storage 업로드
    emotions.py  감정 이름 → 에모티콘 이미지 매핑(원본에서 그대로 추출)
    assets/      폰트 5, 에모티콘 46, 배경·삽화 9
```

`_lib` 는 밑줄로 시작해서 Vercel 이 라우트로 잡지 않는다.

PDF 는 **한 번에 한 권씩** 만든다. 여러 권이면 화면이 순서대로 호출한다 —
요청 하나가 길어져 타임아웃에 걸리는 걸 피하고 진행 상황도 보여줄 수 있다.

## 마음일기 API 에서 겪은 것들

`https://diaryapi.seamspace.me`. Postman 컬렉션
(`MindDiary/mDiary_parents/*.postman_collection.json`)이 있지만 **현재 서버와 다른
부분이 있다.** 아래는 2026-08 기준 실제 응답으로 확인한 내용이다.

**로그인 토큰은 응답 본문이 아니라 쿠키로 온다.**
`POST /mDiary_app/login/` 의 응답 본문에는 `token` 필드가 아예 없다
(Postman 문서에는 `"token": "aaaaa"` 로 적혀 있다). 실제 JWT 는 `set-cookie` 의
`ss_access_token` 이다. CRM 의 `create-coupon` Edge Function 도 같은 방식으로 꺼내 쓴다.
실제 본문 키: `detail, username, name, role, current_group, is_apply_coupon, server_status`.

**응답의 `role` 로 관리자를 판별할 수 없다.** 관리 작업에 쓰는 계정도 `role: "user"` 로
내려온다. 그래서 `PRINT_ADMIN_USERNAMES` 허용목록으로 막는다. 환경변수가 없으면
아무도 통과하지 못한다(열어 두는 것보다 안전한 쪽).

**조회 대상은 JWT 주체가 아니라 요청 본문의 `username` 으로 정해진다.**
`POST /mDiary_app/diary/` 가 그렇다. 즉 서버 쪽에서 교차 조회를 막고 있는지 확인되지
않았다. 화면 단속만으로는 부족해서 서버에서 한 번 더 거른다.

**`from_date` / `to_date` 범위 조회는 동작한다.** 실계정으로 확인했다(3~5월 조회 시
0건, 전체 조회 72건). 그래도 서버가 이 필터를 다르게 해석할 때를 대비해, 결과가
두 달 이상에 걸치지 않으면 `year`+`month` 월별 루프로 떨어진다.

**날짜 형식이 섞여 나온다.** `...Z`, `...(.%f)Z`, `YYYY-MM-DD HH:MM:SS` 세 가지.
`parse_api_date()` 가 전부 받고 **tz 없는 naive** 로 돌려준다. 원본이 UTC 표기를
그대로 벽시계로 취급했고 지금까지 인쇄된 책이 전부 그 기준이라 같은 동작을 유지한다.
여기서 KST 로 바꾸면 자정 근처 일기의 날짜가 하루씩 밀린다.

## 렌더러 — 원본에서 바꾼 것과 그 이유

좌표·색상·폰트 크기는 인쇄 템플릿 값이라 **그대로 뒀다.** 실행 구조만 바꿨다.

**한 캔버스에 이어 그린다.** 원본은 일기마다 캔버스를 새로 만들어 `temp/` 에 저장하고
PyPDF2 로 합쳤다. 그러면 배경 PNG(50KB)가 페이지마다 새로 임베드된다. 한 캔버스에서
`showPage()` 로 넘기면 reportlab 이 같은 파일명 이미지를 한 번만 저장한다.
300페이지 기준 15MB → 0.9MB, 페이지당 증가분 1.5KB. 덤으로 `temp/`·`diary/` 디렉토리와
PyPDF2 의존이 사라지고, 연간 합본이 월별 파일로 흩어지던 원본 버그도 같이 해결된다.

**줄간격을 글자 크기에 비례시켰다.** 원본은 글자가 줄어도 `leading` 을 12pt(토닥토닥
11pt)로 고정했다. 그러면 leading 이 높이를 지배해서 축소 루프가 높이를 거의 못 줄이고,
그래서 애초에 줄간격을 빡빡하게 잡을 수밖에 없었다. 비율로 바꾸니 넉넉히 주면서도
넘칠 때 확실히 줄어든다. 주제 1.25 / 본문 1.45 / 토닥토닥 1.35 배.

**글 잘림 두 가지.** ① 프레임 여백(상하좌우 6pt)을 빼고 재도록 했다. 원본은 프레임
크기 그대로 재서 토닥토닥은 높이 75pt 까지 통과시키는데 실제 공간은 68pt 뿐이었고,
그 사이에 걸린 글은 `Frame.addFromList` 가 조용히 버렸다. ② 최소 크기(6pt)까지 줄여도
안 들어가면 `KeepInFrame` 으로 통째로 축소해 넣는다. 원본은 이 경우에도 버렸다.

**축소 루프에 하한을 뒀다.** 원본은 탈출 조건이 없어 긴 일기에서 무한 루프가 가능했다.
로컬에선 그냥 멈추지만 서버리스에선 타임아웃까지 과금된다.

**사용자 텍스트를 이스케이프한다.** `Paragraph` 가 미니 HTML 을 파싱해서 일기에
`<` 나 `&` 가 있으면 글자가 사라지거나 예외가 났다.

**에셋 경로를 `__file__` 기준으로 바꿨다.** 원본은 전부 상대 경로라 CWD 가 repo 루트일
때만 동작했다.

**삽화 교대 상태를 인자로 주고받는다.** 원본은 전역이라 동시 요청에서 섞였다.

**렌더 불가 항목.** `traffic` 이 GREEN/YELLOW/RED 가 아니면 페이지가 안 생긴다.
그냥 두면 견적 100p / 인쇄 98p 가 되므로 `is_renderable()` 로 세고 화면에 경고를 띄운다.
`stats` 와 `generate` 가 반드시 같은 함수로 센다.

## 이모지

**흑백이다. reportlab 이 컬러 이모지 폰트를 못 쓴다.** TTF 파서가 외곽선(glyf)만 읽는데
컬러 이모지는 비트맵(CBDT)이나 COLR 레이어에 들어있다. 저장소에 있던
`NotoColorEmoji.ttf` 는 COLR **v1** + SVG 형식이라 Pillow/FreeType 으로도 렌더 픽셀이
0이었다. 원본 `reportsD.py` 에 이 폰트가 등록만 되고 쓰이지 않은 채 남아 있던 것도
같은 이유로 보인다.

컬러를 넣으려면 이모지를 PNG 로 그려 `<img>` 로 끼우는 방법뿐인데, 이건
`wordWrap='CJK'` 와 같이 못 쓴다 — reportlab 의 CJK 줄바꿈 코드가 조각마다 `ord()` 를
호출하는데 이미지 조각에는 글자가 없어 그대로 죽는다(`paragraph.py cjkFragSplit`).
한글은 CJK 줄바꿈 없이는 프레임 밖으로 넘치므로 그쪽을 포기할 수 없다.

그래서 **Noto Emoji(흑백 외곽선, OFL, 859KB)** 를 쓴다. 이모지가 '글자'로 취급되니
줄바꿈과 충돌하지 않고 벡터라 인쇄 해상도에서 깨지지 않는다. 글자 크기의 85% 로 그린다
(Noto Emoji 글리프는 em 사각형을 꽉 채우는데 한글은 여백이 있어 같은 pt 면 이모지만
커 보인다).

판별은 코드포인트 범위로 후보를 고른 뒤 **폰트 수록 여부로 확정**한다. 범위가 조금
틀려도 한글이 이미지로 바뀌는 사고가 나지 않는다. 폰트에 없는 이모지는 지운다
(남기면 본문 폰트에서 네모박스가 된다). 피부톤·이형자선택자·ZWJ 는 떼어낸다.
결합 이모지(👨‍👩‍👧)는 낱개로, 국기는 제거된다 — reportlab 이 GSUB 합자를 적용하지 않는다.

참고로 실제 일기 72건에 등장한 이모지 60종은 전부 이 폰트에 있었다(제거 0종).

## 저장과 다운로드

PDF 는 Supabase Storage `diary_prints` 버킷에 올리고 30분짜리 signed URL 로 내려받는다.

응답 본문에 직접 실을 수도 있지만 **Vercel 서버리스 응답 상한이 4.5MB** 다. 실측상
300페이지 책이 글자 다양성에 따라 2.8MB 안팎이고 JSON base64 로 싸면 3.7MB 라 여유가
없다(반복 문장으로 재면 0.9MB 로 나와서 착각하기 쉽다).

**버킷은 비공개다.** PDF·MIME 제한, 50MB 상한. `shop_*` 테이블은 anon 키에 열려 있지만
여기 들어가는 건 사용자가 쓴 일기 본문이라 같은 정책을 따라가면 안 된다.
서버(service_role)만 읽고 쓴다 — 정책을 하나도 만들지 않으면 그렇게 된다.

## 가격과 분권

`_lib/pricing.py`. `/shop` 의 `diary` 상품과 같은 값이므로 **한쪽만 고치면 안 된다.**

| 페이지 | 가격 |
|---|---|
| 36~100 | 26,000 |
| 101~150 | 29,000 |
| 151~200 | 32,000 |
| 201~250 | 35,000 |
| 251~300 | 38,000 |

배송비 3,500원(주문당 1회). 36편 미만은 인쇄 불가.

300p 를 넘으면 **월 경계를 넘지 않게 균등 분할**한다. 앞에서부터 채우면 340p 가
300/40 이 되어 2권째가 최소 36p 미달로 인쇄 불가가 된다. 균등 분할이면 170/170.
한 달은 많아야 31편이라 월 단위로 끊어도 300 이하 구성이 항상 가능하다.
사용자가 경계를 직접 정할 수도 있다(`splits`).

## 운영

**환경변수** (Vercel 프로젝트)
- `PRINT_ADMIN_USERNAMES` — 쉼표 구분. **없으면 아무도 로그인 못 한다.**
- `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` — 없으면 `VITE_` 접두사 버전으로 떨어진다
  (이 프로젝트는 서버용 키도 `VITE_` 로 들어 있다. 화면 코드에서 서비스롤 키를 참조하면
  Vite 가 번들에 박아 브라우저로 내보내므로 **절대 참조하지 말 것**)
- `MDIARY_BASE_URL` — 기본값 `https://diaryapi.seamspace.me`

**최초 1회**: `supabase/create_diary_prints_bucket.sql` 실행

**주의**: `vercel deploy` 는 배포마다 새 URL 을 만들고 예전 URL 은 예전 코드를 계속
서비스한다. 운영 주소는 `https://seamspace-crm-hub.vercel.app/print` 다.
화면 하단에 빌드 해시와 환경이 표시되고, 운영이 아니면 상단에 경고가 뜬다.

**요금제**: Vercel Hobby 라 함수 실행 상한이 60초다. 72페이지 생성이 약 7초라 여유가
있지만, 300페이지 한 권이면 20~30초대로 올라갈 수 있다.

## 검증 방법

인쇄물이라 "돌아간다"로는 부족하다. 아래 방식으로 확인했고, 렌더러를 고칠 때 같은
방법을 다시 쓰면 된다.

**원본과 시각적으로 같은지**: 원본 `reportsD.py` 를 그대로 돌린 PDF 와 새 렌더러 출력의
그리기 연산을 비교한다. 폰트 서브셋 번호가 달라 바이트 비교는 무의미하므로,
**그래픽 상태를 추적해 각 그리기 시점의 유효 색상·좌표·글자수·투명도**를 비교한다.
신호등 3색 × 반쪽/전면 레이아웃, 일요일 요일박스 분기, 삽화 교대, 긴 주제 y보정,
MBTI 유무를 태운 표본으로 전 항목 일치를 확인했다.

**글이 잘리지 않는지**: 렌더한 PDF 에서 텍스트를 추출해 입력의 **끝 문장**이 남아
있는지 본다. 보통 길이 / 반페이지 경계 / 한 페이지 가득 / 4,400자 / 띄어쓰기 없는
3,000자 / 이모지 600개 / 여러 줄 주제. (이모지는 추출기가 못 읽으므로 한글 끝말로 확인)

**프레임을 벗어나지 않는지**: content stream 의 `BT`/`Tm`/`TL`/`T*` 를 따라가며 줄마다의
페이지 좌표를 계산해 프레임 밖 좌표가 있는지 본다. `Tm` 은 문단마다 한 번만 나오고
줄바꿈은 `T*` 로 처리되므로 `Tm` 만 세면 대부분의 줄을 놓친다.

**페이지 수 = 일기 수**: `c.save()` 가 끝에 빈 페이지를 붙이지 않는지 확인한다.
가격이 페이지 수로 정해지므로 한 장만 어긋나도 금액이 틀린다.

  저장소에 참조 없이 남아 있는 걸 보면 예전에 구상됐다가 접힌 설계로 보인다

## 확인이 필요한 것 (인쇄소)

- **제본 시 페이지 수가 4의 배수여야 하는지.** 일기 1개 = 1페이지라 임의 개수가 나온다.
  빈 페이지를 채워야 한다면 그게 가격 구간을 넘길 수도 있다(300p → 304p).
- **표지·속지가 가격표의 페이지 수에 포함되는지.** 지금 견적은 본문만 센다.
